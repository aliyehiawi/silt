# Memory Management

Memory makes the agent a long-term collaborator — someone who speaks your internal language across both work and personal life.

> **The canonical map of folders, files, and naming conventions lives in [[memory/README.md|Memory README]]. This skill covers the lookup/update *behavior*; the architecture is defined there.**

## Graph Convention

This vault is now an Obsidian-compatible knowledge graph. Three core rules:

1. **YAML frontmatter** at the top of every entity file — contains type, title, aliases, status, created/updated dates, and type-specific fields (role, team, dates, etc.). See examples below.

2. **Path-based wiki-links** for internal cross-references: `[[path/to/file.md|Display text]]` format. Use these instead of bare prose or `[markdown](links)`. External URLs (https://) stay as standard markdown.

3. **`## Linked from` footer** at the end of every file — auto-generated by `python3 system/scripts/transform.py` to list every file linking INTO this one. Lets you trace inbound references without Obsidian.

For the full specification, see [[memory/README.md|Memory README]] § "Graph convention".

## The Goal

Transform shorthand into understanding:

```
User: "ask todd to do the PSR for oracle"
              ↓ Agent decodes
"Ask Todd Martinez (Finance lead) to prepare the Pipeline Status Report
 for the Oracle Systems deal ($2.3M, closing Q2)"
```

Without memory, that request is meaningless. With memory, the agent knows:
- **todd** → Todd Martinez, Finance lead, prefers Slack
- **PSR** → Pipeline Status Report (weekly sales doc)
- **oracle** → Oracle Systems deal, not the company

## Universal preview rule

**Every write to the memory tree, journal cross-files, CLAUDE.md, or task files goes through preview → confirm → write. No exceptions — including one-liner shortcuts like `remember:` or `X means Y`.**

Preview format:

```
Proposed changes:
- memory/work/companies/{co}/people/sarah.md      (append Log line)
- memory/work/companies/{co}/projects/phoenix.md  (append Log line)
- memory/work/companies/{co}/tasks/active/pricing-rollout.md
    → done/2026-04-pricing-rollout.md             (move + Log)
- CLAUDE.md                                       (promote sarah to hot cache)

Apply? [y / n / edit]
```

- `y` → write all proposed changes
- `n` → discard everything, nothing is written
- `edit` → user inline-edits the proposed diff, then y/n

**The only auto-write exception** is appending the raw journal entry to `journal/{YYYY}/{YYYY-MM}/{YYYY-MM-DD}.md`. That file is an immutable log and cannot be "wrong" — anything you type is your record of what you said. Everything *derived* from that entry (entity cross-files, task moves, CLAUDE.md promotions, memory merges, consolidations) is previewed.

This rule applies uniformly across all skills — journal, update, start, task-management, consolidate-memory, and any ad-hoc `remember:` / `X means Y` shortcut.

## Architecture

```
CLAUDE.md                       ← Hot cache (~30 entities across work + life)
TASKS.md                        ← Task dashboard (pointer-index over task files)
journal/                        ← Immutable chronological log (daily entries)
memory/
  README.md                     ← Authoritative map of this tree
  me.md                         ← Core identity + milestones + current state
  glossary.md                   ← Unified decoder ring (work + life)
  all-entities.md               ← Master TOC of every entity
  preferences.md                ← Cross-domain preferences
  work/
    _current.md                 ← Pointer to current employer
    companies/{slug}/           ← One folder per employer/client
      {slug}.md                  ← Company entity (was README.md before convention 1.1) — overview, role, team, tools, rituals
      people/{name}.md
      projects/{name}.md
      tasks/                    ← One file per task (see task-management)
        active/{slug}.md
        waiting/{slug}.md
        done/{YYYY-MM-slug}.md
        done/archive/{YYYY}/
      glossary.md               ← Company-specific jargon
  life/
    people/{family,friends,flatmates}/{name}.md
    places/{name}.md            ← Prefecture, clinics, cafés, gyms
    orgs/{name}.md              ← Bank, insurance, landlord, gov
    topics/{name}.md            ← Ongoing life matters (visa, apt hunt)
    events/{YYYY-name}.md       ← Trips, weddings, milestones
    health/{providers,log,conditions}
    home/{current,past}
```

**CLAUDE.md (Hot Cache):**
- Top ~15 work contacts + ~15 life people (family + close friends)
- ~30 most common acronyms/terms across both domains
- Active work projects (5–10) and active life topics (3–5)
- Your preferences
- **Goal: Cover 90% of daily decoding needs in ~100 lines**

**memory/glossary.md (Full Glossary):**
- Complete decoder ring — every acronym, nickname, codename across work + life
- Searched when something isn't in CLAUDE.md
- Can grow indefinitely

**memory/work/companies/{slug}/, memory/life/*/:**
- Rich detail when needed for execution
- Full profiles, history, context
- Grows alongside you over years — companies archive when you leave, life entities accumulate dated Log lines

## Lookup Flow

```
User: "ask todd about the PSR for phoenix"

1. Check CLAUDE.md (hot cache)
   → Todd? ✓ Todd Martinez, Finance
   → PSR? ✓ Pipeline Status Report
   → Phoenix? ✓ DB migration project

2. If not found → search memory/glossary.md and memory/all-entities.md
   → Full glossary has every term; index has every entity + location

3. If still not found → ask user
   → "What does X mean? I'll remember it."
```

For life-domain lookups ("did I ever see Dr. Smith?", "when did I last visit the prefecture?"), the same tiered lookup applies against `life/`:

```
1. CLAUDE.md hot cache
2. memory/all-entities.md → resolve entity → open file → read Log section
3. If entity doesn't exist → ask user, then stub it
```

This tiered approach keeps CLAUDE.md lean (~100 lines) while supporting unlimited scale across decades of journal entries.

## File Locations

- **Working memory:** `CLAUDE.md` in current working directory
- **Deep memory:** `memory/` subdirectory — see [[memory/README.md|Memory README]] for the full tree and decision rules
- **Daily log:** `journal/YYYY/MM/YYYY-MM-DD.md` — immutable, append-only

## How to Interact

### Decoding User Input (Tiered Lookup)

**Always** decode shorthand before acting on requests:

```
1. CLAUDE.md (hot cache)        → Check first, covers 90% of cases
2. memory/glossary.md + index.md → Full decoder + entity map
3. memory/work/... or life/...   → Rich detail when needed
4. Ask user                      → Unknown term? Learn it.
```

Example:
```
User: "ask todd to do the PSR for oracle"

CLAUDE.md lookup:
  "todd" → Todd Martinez, Finance ✓
  "PSR" → Pipeline Status Report ✓
  "oracle" → (not in hot cache)

memory/glossary.md lookup:
  "oracle" → Oracle Systems deal ($2.3M) ✓

Now the agent can act with full context.
```

### Adding Memory

When user says "remember this" or "X means Y", or when the journal skill cross-files, **build the proposed diff and show it before writing** (per [[#universal-preview-rule|§ Universal preview rule]]). Even a single-line glossary add is previewed — the diff is just one line.

1. **Glossary items** (acronyms, terms, shorthand):
   - Add to `memory/glossary.md` (if cross-domain) or `memory/work/companies/{co}/glossary.md` (if company-specific)
   - If frequently used, promote to CLAUDE.md Terms section

2. **Work people:** `memory/work/companies/{co}/people/{name}.md`
3. **Family / friends / flatmates:** `memory/life/people/{family|friends|flatmates}/{name}.md`
4. **Work projects:** `memory/work/companies/{co}/projects/{name}.md`
5. **Places:** `memory/life/places/{name}.md`
6. **Organizations (non-employer):** `memory/life/orgs/{name}.md`
7. **Health providers:** `memory/life/health/providers/{name}.md`
8. **Ongoing life topics:** `memory/life/topics/{name}.md`
9. **Bounded events:** `memory/life/events/{YYYY-name}.md`
10. **Preferences:** CLAUDE.md Preferences section + `memory/preferences.md`
11. **Tasks:** `memory/work/companies/{co}/tasks/{active,waiting,done}/{slug}.md` — one file per task (see [[task-management/SKILL.md|Task Management Skill]])

For all entity files:
- **Always wiki-link cross-references** — use `[[path/to/file.md|Display text]]` format instead of bare prose or relative paths
- **YAML frontmatter at the top** — type, title, aliases, status, dates, and type-specific fields
- **Capture nicknames / aliases** in the frontmatter `aliases:` field — critical for decoding
- **Append Log lines dated YYYY-MM-DD** rather than rewriting sections. Dated lines compound into a timeline
- **Never create `misc.md` or `other.md`.** If you can't decide where something goes, ask

Full decision tree is in [[memory/README.md|Memory README]].

### Recalling Memory

When user asks "who is X" or "what does X mean":

1. Check CLAUDE.md first
2. Check memory/ for full detail
3. If not found: "I don't know what X means yet. Can you tell me?"

### Progressive Disclosure

1. Load CLAUDE.md for quick parsing of any request
2. Dive into memory/ when you need full context for execution
3. Example: drafting an email to todd about the PSR
   - CLAUDE.md tells you Todd = Todd Martinez, PSR = Pipeline Status Report
   - memory/people/todd-martinez.md tells you he prefers Slack, is direct

## Bootstrapping

Use `/productivity:start` to initialize the directory scaffold and `CLAUDE.md`. It can optionally scan your chat, calendar, email, and documents to seed work people and projects.

Daily ritual is `/productivity:journal` (or `/journal`) — a free-dump entry that auto-parses and cross-files into the memory tree above. That's how memory actually grows over years.

## Conventions

- **Bold** terms in CLAUDE.md for scannability
- Keep CLAUDE.md under ~100 lines (the "hot 30" rule)
- Filenames: lowercase, hyphens (`todd-martinez.md`, `project-phoenix.md`)
- Always capture nicknames and alternate names in frontmatter
- Glossary tables for easy lookup
- When something's used frequently, promote it to CLAUDE.md
- When something goes stale, demote it to memory/ only
- **After any batch write**, run `python3 system/scripts/transform.py` from the workspace root to refresh wiki-links and regenerate `## Linked from` sections across the vault. The script is idempotent.

| Work project | Active only | work/companies/{co}/projects/{name}.md |
| Life topic | Active only (3–5) | life/topics/{name}.md |
| Nickname | If associated person is in hot cache | glossary.md (all nicknames) |
| Place (prefecture, clinic, etc.) | Key ones only | life/places/{name}.md |
| Organization (bank, insurance, etc.) | Key ones only | life/orgs/{name}.md |
| School / institution | All of them (current + past) | life/orgs/{slug}.md (e.g. your-university.md, grad-program.md, high-school.md) |

| Active / recent tasks | Active + waiting + last 30 days done | TASKS.md (dashboard over work/companies/{co}/tasks/) |
| Historical / stale | ✗ Remove | ✓ Keep in memory/ (never delete) |

## Promotion / Demotion

**Promote to CLAUDE.md when:**
- You use a term/person frequently
- It's part of active work or an active life topic

**Demote to memory/ only when:**
- Project / life topic closed out
- Person no longer frequent contact
- Term rarely used

This keeps CLAUDE.md fresh and relevant. Full records stay in `memory/` forever — nothing is ever deleted, only archived.

## Archival (long-term hygiene)

When something ends (left a job, finished a life topic, moved out of an apartment):

- Update `status:` in the frontmatter (`past`, `archived`, `closed`)
- Move to a sibling `archive/` directory if the active folder is getting crowded: e.g. `life/topics/archive/old-visa.md`
- Keep cross-references working by updating `memory/all-entities.md`
- **Never delete.** Future-you will want that record.

When a single entity's Log exceeds ~500 lines (a gym you've gone to for 10 years), split: the last 2 years stay in `{name}.md`, older entries move to `{name}-archive-{YYYY}.md` with a pointer from the main file.
