# Update Command

> If you see unfamiliar placeholders or need to check which tools are connected, see [[CONNECTORS.md|CONNECTORS]].

Keep your task files and memory current. Two modes:

- **Default:** Sync open tasks from the company wiki into task files, triage stale ones, check memory for gaps, reconcile the journal.
- **`--comprehensive`:** Default plus a chat scan to discover new teammates (people-only — never extracts messages or tasks from chat).

## Usage

```bash
/productivity:update
/productivity:update --comprehensive
```

## Default Mode

> **Graph convention.** Every file written by this skill follows the vault's Obsidian-style graph convention: YAML frontmatter at top, path-based wiki-links for cross-references, `## Linked from` footer regenerated by the transform script. Full spec in [[memory/README.md|Memory README]] § "Graph convention".

> **Every write in every step below goes through preview → confirm → write**, per [[memory-management/SKILL.md|Memory Management Skill]] § Universal preview rule. Reads and fetches are free; any file creation, move, edit, or TASKS.md update is proposed as a diff and only applied on `y`.

### 1. Load Current State

Read `TASKS.md`, `memory/` directory, and `journal/` (last 30 days). If any are missing, suggest `/productivity:start` first.

### 2. Sync Tasks from the Company Wiki

> **External sources are ephemeral inputs.** Nothing from the wiki or chat is stored on disk as a link, ID, or index. See [[memory/README.md|Memory README]] → "External sources — ephemeral inputs".

Check for an available company-wiki connector (Notion, Confluence, Google Docs, etc.). If none, skip this step.

**Source:** the tasks page / database the user hands you each week (the page that lists tasks assigned to them). User confirms which page to use the first time; the skill remembers the choice for this company in-session.

#### 2a. Fetch open tasks assigned to the user

Query the wiki for the tasks page. For each task:

1. **Title** — the task slug (normalized to `lowercase-hyphen`).
2. **Description** — the ticket body, distilled to plain prose (not copy-pasted raw). No URL retained.
3. **Due date** — if present.
4. **Project** — inferred from task metadata, tags, or explicit relation. Maps to an existing `projects/{slug}.md` if possible.
5. **Status** — open / in progress / done.

#### 2b. Reconcile with local task files

Tasks live as **files**, not TASKS.md lines. Location: `memory/work/companies/{co}/tasks/{active,waiting,done}/{slug}.md`.

**The full reconciliation result is batched into one preview** — all proposed creates, moves, description refreshes, and TASKS.md edits shown together with `Apply? [y / n / edit]`. Nothing writes until the user approves.

| Wiki task | Local state | Action |
|-----------|-------------|--------|
| Open, no file in `active/` or `waiting/` | Not tracked | Create `tasks/active/{slug}.md` with Description seeded from ticket; add line to `TASKS.md` dashboard |
| Open, already in `active/` or `waiting/` | Tracked | No change. Offer to refresh Description *only* if the ticket body changed substantially. Never touch the Log. |
| Done in wiki, in `active/` or `waiting/` locally | Out of sync | Propose move to `tasks/done/{YYYY-MM-slug}.md` with today's `Completed:` date. Move the TASKS.md line to Done (last 30 days). |
| In `active/` locally, not in wiki at all | Possibly stale | Flag: "Still working on this?" Don't auto-archive. |

See [[task-management/SKILL.md|Task Management Skill]] for the exact file format, slug rules, and move semantics.

#### 2c. Task files are plain — no wiki metadata, but DO use wiki-links to entities

Every task file contains only your prose:
- YAML frontmatter (`type:`, `title:`, `status:`, `created:`, `due:`, `project:`, `updated:`, `tags:`).
- Description (plain paragraph, distilled from the ticket).
- Log (appended by `/journal` entries as you work).

**No** `Source:`, `URL:`, `Page ID:`, `Last synced:`, or any other wiki-originating field. The wiki is a transient source; once the task file is written, there's no reference back.

**But the Description and Log MUST wiki-link any entity it mentions** — projects, people, sibling tasks. This is what makes the task a real graph node, not an isolated leaf. See [[memory/README.md|Memory README]] § Rule 4 ("Link entities to each other, not just through TOCs"). Concretely, a Description like:

> "fix the data race in Phoenix's loader. Sarah flagged it last week."

becomes:

> "fix the data race in [[memory/work/companies/{co}/projects/phoenix.md|Phoenix]]'s loader. [[memory/work/companies/{co}/people/sarah-chen.md|Sarah]] flagged it last week."

#### 2d. Task-triggered stubs

If a task's Description mentions:
- A **project** that doesn't have a file → propose a thin `projects/{slug}.md` stub (name + status:active + one-line summary). Wiki-link the new stub from the task body.
- A **person** not in `people/` → propose a stub (name + role if inferable). Chat sync will usually beat this to it. Wiki-link from the task body.

Always ask; don't auto-stub.

#### 2d.5. Entity cross-link sweep (after creating new task files)

If 2a–2d created or refreshed task files, run a focused cross-link sweep over those files (not the whole vault):

1. Build a slug registry from `memory/work/companies/{co}/`'s existing entities (projects, people, how-tos, glossary terms).
2. For each new/refreshed task's Description and Log, find plain-text mentions of registered entities and replace with wiki-links (case-insensitive, word-boundary). Skip mentions inside fenced code blocks. If a name is ambiguous (two "Sarah"s), don't auto-link — ask.
3. Run `python3 system/scripts/transform.py` so every project / person now shows the new task in its `## Linked from` section.

This is the same pass [[start/SKILL.md|start]] runs after the first-time scrape — keeps the graph from drifting back into TOC-shape as new tasks come in.

#### 2e. First-time company-wiki scrape (one-time, when onboarding a company)

This is **not** part of the weekly `/update` flow. It happens once when a new company is being set up. The first time, it runs as part of [[start/SKILL.md|/start]]; for any subsequent employer / side job / client, run [[onboard-company/SKILL.md|/onboard-company]]. The full flow is documented in [[onboard-company/SKILL.md|onboard-company/SKILL.md]] § 4; summarized here:

- User hands the agent the company home page.
- The agent walks **all reachable pages, all levels**, classifying each: company overview / project / team / people / past-task / glossary / social / skip (confidential or handbook).
- The agent asks which team the user is on, for depth calibration (own-team projects get richer summaries).
- Extracts into: `companies/{co}/{co}.md`, `companies/{co}/projects/{slug}.md` (one per product/project), `companies/{co}/people/{name}.md` (team + adjacent), `companies/{co}/glossary.md`, `companies/{co}/tasks/done/{YYYY-MM-slug}.md` (for user's past/closed tasks).
- **Skips:** active tasks currently assigned to the user (those come through weekly sync in 2a–2d), confidential pages, HR/comp, customer-specific pages, handbook/policies.
- Every file is plain prose, dated, no wiki metadata.

On a typical mid-sized company this produces a few hundred files totaling a few MB. After it runs once, the weekly `/update` only needs to touch the tasks page.

### 2f. Other task sources (if no wiki connector)

If there's no wiki connector but other task sources are available:
- **Project tracker** (Asana, Linear, Jira) — same flow as 2a–2d, tool-agnostic.
- **GitHub Issues** (if in a repo): `gh issue list --assignee=@me` — same flow.
- **Manual TASKS.md edits** — nothing to sync; just read.

All of these feed the same task-files-are-files model. No external IDs stored.

### 3. Triage Stale Items

Review Active tasks in TASKS.md and flag:
- Tasks with due dates in the past
- Tasks in Active for 30+ days
- Tasks with no context (no person, no project)

Present each for triage: Mark done? Reschedule? Move to Someday?

### 4. Decode Tasks for Memory Gaps

For each task, attempt to decode all entities (people, projects, acronyms, tools, links):

```
Task: "Send PSR to Todd re: Phoenix blockers"

Decode:
- PSR → ✓ Pipeline Status Report (in glossary)
- Todd → ✓ Todd Martinez (in people/)
- Phoenix → ? Not in memory
```

Track what's fully decoded vs. what has gaps.

### 5. Fill Gaps

Present unknown terms grouped:
```
I found terms in your tasks I don't have context for:

1. "Phoenix" (from: "Send PSR to Todd re: Phoenix blockers")
   → What's Phoenix?

2. "Maya" (from: "sync with Maya on API design")
   → Who is Maya?
```

Add answers to the appropriate memory files (people/, projects/, glossary.md).

### 6. Capture Enrichment

Tasks often contain richer context than memory. Extract and update:
- **Links** from tasks → add to project/people files
- **Status changes** ("launch done") → update project status, demote from CLAUDE.md
- **Relationships** ("Todd's sign-off on Maya's proposal") → cross-reference people
- **Deadlines** → add to project files

### 7. Journal Reconciliation

Quick check:
- List any days in the last 14 with no journal entry → surface them: "No entries on 2026-04-20 or 2026-04-22 — want to backfill from memory or skip?"
- Scan the last 7 daily entries for parsed entities that *don't* have a corresponding memory file (possible missed cross-file during `/journal`). Propose stubbing them.
- Scan entity files for ones whose Log hasn't been touched in 90+ days despite appearing in recent journal entries → propose re-linking.

Keep this light — don't rewrite journal entries, don't auto-create stubs, just surface gaps.

### 8. Report

```
Update complete:
- Tasks: +3 from project tracker (e.g. Asana), 1 completed, 2 triaged
- Memory: 2 gaps filled, 1 project enriched
- Journal: 12/14 days logged; 2 proposed entity stubs
- All tasks decoded ✓
```

## Comprehensive Mode (`--comprehensive`)

Everything in Default Mode, plus a people-discovery sweep of chat and (if relevant) a light journal reconciliation over a wider window.

### Extra Step: Chat sync (people discovery only)

Goal: find new teammates you've started working with but haven't stubbed yet. **Only** used for the people section of the current company.

The candidate list is shown as a preview. The user approves per-person (`y/n/skip`) and no person file is created until they do. Per-person prompts count as the universal preview gate for this step.

Query the company chat tool (Slack, Teams, etc.) for:
- **Direct-message partners** — people you've DM'd (either direction) in the last 90 days
- **@mentions of you** — people who pinged you
- **People you @mentioned** — people you tagged in messages

Deduplicate into a candidate list. For each person:

1. **Already in `work/companies/{co}/people/`?** → Skip. No Log line from chat, ever. Log lines come from journal entries only.
2. **Not yet stubbed?** → Fetch their profile (name, role, team) via the chat tool's profile API — not their messages. Propose:

```
New people from chat (last 90 days):

1. Maya Rodriguez — Senior designer, Platform team
   12 DMs with you, 3 @-mentions
   → Stub? (y/n/skip)

2. Alex K — Backend engineer, Infra team
   4 DMs, 0 @-mentions
   → Stub? (y/n/skip)
```

On confirm → create `work/companies/{co}/people/{name}.md` with name, role, team, dates. **No chat ID, no profile URL, no "first messaged on" from chat.** If the user wants "first DM'd" as a fact, they can write it in the journal; but the scan itself doesn't record chat metadata.

### What chat sync does NOT do

- Does not extract commitments or todos from messages
- Does not read channel content
- Does not list channels
- Does not store any message, snippet, or chat metadata to disk
- Does not update existing people's Log lines

Chat is a people-discovery tool. Commitments and todos are captured when you journal them or when they appear on the wiki tasks page.

### Extra Step: Journal reconciliation (wider window)

Same as default-mode step 7 but over 30 days instead of 14. Lists:
- Days with no journal entry
- Entities mentioned in recent entries that don't have a memory file
- Entity files stale 90+ days

### Notes

- Never auto-add tasks, people, or memories without user confirmation
- **No external source metadata is ever written to disk** (no URLs, IDs, "last synced" timestamps, index files)
- Fuzzy matching on task titles handles minor wording differences
- Safe to run frequently — only updates when there's new info
- `--comprehensive` always runs interactively

## Graph maintenance scripts

Three scripts in `outputs/` keep the Obsidian graph clean. As part of `/update`, run them in order:

### 1. Transform (mandatory)

```
python3 system/scripts/transform.py
```

Idempotent — normalizes YAML frontmatter, converts any new path references to wiki-links, regenerates `## Linked from` sections across the vault. Run after any batch of writes.

### 2. Repair broken links (only if needed)

```
python3 system/scripts/repair_links.py
```

Walks every `[[path|alias]]` and tries to repair targets that don't resolve (basename lookup, prefix-strip heuristics). Run if `transform.py` reports broken links or if you've moved files.

### 3. Audit (weekly health check)

```
python3 system/scripts/audit.py
```

Diagnostic tool — does NOT modify files. Reports per subgraph (one bucket per company, plus life family / friends / events / topics / places / orgs / health / home) every file with:

- **ORPHAN** (0 inbound, 0 outbound semantic edges) — file isn't connected to anything
- **only-inbound** (mentioned by peers but doesn't link out itself) — body needs wiki-links
- **only-outbound** (links out but nothing links back) — peer files need to reference it
- **FM:created,updated** (missing frontmatter dates)

Run as part of `/update` to catch drift early. Hub TOC files (`memory/life/context.md`, `memory/preferences.md`) and journal entries are correctly skipped — they're meant to be only-outbound.

If audit reports issues:
1. **ORPHAN / only-inbound / only-outbound** → enrich the file's body with wiki-links to peers it's actually related to (companions, parent project, etc.). See [[memory/README.md|Memory README]] § Rule 4.
2. **Missing frontmatter** → add `created:` / `updated:` / `type:` per the spec.
3. After fixing, re-run `transform.py` and then `audit.py` again — issue count should drop to 0.

**Frequency:** run audit every `/update` (weekly). It's read-only and fast (< 1 second on hundreds of files).
