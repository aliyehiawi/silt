# Onboard Company

Add a new company (employer, contracting client, or side job) to an already-initialized booklet. This skill is what `/start` does for the *first* company, but factored out so it can be run any number of times as the user's career evolves.

> If you've never run `/start` and `CLAUDE.md` doesn't exist yet, run [[start/SKILL.md|/start]] first — it bootstraps the whole vault and onboards the first company in one pass. This skill assumes the vault is already initialized.

> **Graph convention.** Every file written follows the vault's Obsidian-style graph convention: YAML frontmatter at top, path-based wiki-links for cross-references, `## Linked from` footer regenerated by `python3 system/scripts/transform.py`. Full spec: [[memory/README.md|Memory README]] § "Graph convention".

> **Universal preview rule.** Every content-bearing write batches into one preview ending with `Apply? [y / n / edit]`. Empty-directory scaffolding is exempt. Full rule in [[memory-management/SKILL.md|Memory Management Skill]] § Universal preview rule.

> **External sources are ephemeral.** Wiki and chat are input pumps. No URLs, IDs, or "last synced" timestamps land on disk. See [[memory/README.md|Memory README]] → "External sources — ephemeral inputs".

## When to use

| Situation | How to invoke |
|---|---|
| Starting a new full-time job | `/onboard-company <new-slug> --job-change` |
| Picking up a new contracting client / side job | `/onboard-company <slug> --side-job` |
| Onboarding a customer-facing client (not employment) | `/onboard-company <slug> --client` |
| Late-onboarding an existing employer that was never scraped | `/onboard-company <existing-slug>` |

`<company-slug>` is the lowercase-hyphen ASCII slug used everywhere downstream (folder name, frontmatter, wiki-links). Match the convention of any existing companies in your `memory/work/companies/` tree.

## What this skill does NOT do

- Does **not** initialize the vault scaffold (memory tree, dashboard, TASKS.md, journal/). That's [[start/SKILL.md|/start]]'s job.
- Does **not** sync open tasks weekly. That's [[update/SKILL.md|/update]]'s job — once the company is onboarded, weekly `/update` takes over.
- Does **not** rewrite `CLAUDE.md` automatically. CLAUDE.md is the user's hot cache and they decide what gets promoted there. The skill ends with a *suggested* CLAUDE.md diff that the user can apply via the universal preview gate.
- Does **not** decode shorthand from the user's task list. That's part of [[start/SKILL.md|/start]]'s first-run bootstrap. Onboarding a *second* company assumes the user already speaks the system's language; if shorthand decoding is needed it can be triggered manually later.

## Instructions

### 1. Pre-flight checks

Verify the vault is initialized:

- `CLAUDE.md` exists (symlinked to `AGENTS.md`).
- [[memory/README.md|Memory]], [[memory/me.md|Me]], [[memory/all-entities.md|All Entities]], [[memory/work/_current.md| Current]] all exist.
- `journal/` exists.

If any are missing, stop and recommend running [[start/SKILL.md|/start]] first.

Also check whether the company is already partially present:

- `memory/work/companies/{slug}/` — if it exists, this is a re-onboard or late-scrape, not a fresh add. Confirm with the user before merging into existing content.
- Read [[memory/work/_current.md| Current]] to know who the current employer is — needed for the job-change flow.

### 2. Pick the mode

If invoked without a flag, ask one short question:

```
Is {slug} replacing your current employer, a side gig you're keeping
alongside it, or a contracting client engagement?

  [j] Job change — flips current employer to past, updates me.md
  [s] Side job — kept alongside current; me.md is unchanged
  [c] Client — paid engagement, not employment; minimal me.md touch
  [r] Re-onboard existing — already in vault, just scrape what's missing
```

The answer determines which me.md / `_current.md` updates are part of the diff in step 6.

### 3. Scaffold the company folder

Create empty directories (no preview needed — pure scaffolding):

```
memory/work/companies/{slug}/
  people/
  projects/
  tasks/
    active/
    waiting/
    done/
  how-to/      # optional — created on first how-to write
```

Do **not** create `tasks/done/archive/` until needed. Do **not** pre-create empty `glossary.md`, `{slug}.md`, etc. — those are written in step 5 with content.

### 4. Wiki scrape (optional but recommended)

This is the same two-pass flow defined in [[start/SKILL.md|/start]] § 6, summarized here for self-containedness. If no wiki connector is available, skip to step 5.

Offer:

```
I can scrape {company}'s wiki to bootstrap the company folder —
products, teams, people, past tasks, glossary. One-time, takes a few minutes,
produces a few hundred files. Or skip and we'll fill it organically.

Hand me the company home page and I'll go from there.
```

#### 4a. Scope calibration

```
Which team are you on at {company}, and which 1–2 teams do you
collaborate with most? I'll write richer summaries for projects
your team owns and stub the people you work with most often.
```

For a `--client` engagement the question becomes: "Which workstream / contact group are you assigned to?" — same intent, different framing.

#### 4b. Walk the wiki — same classifier as `/start` § 6.B

Starting from the user-provided home page, traverse all reachable pages, all levels, classifying each:

| Class | Action |
|---|---|
| Company overview (home, "about us", mission) | Extract into `work/companies/{slug}/{slug}.md` |
| Product / project page | Stub as `work/companies/{slug}/projects/{p-slug}.md`. Rich Summary for own-team projects; thinner for others. |
| Team page / team roster | Section in `{slug}.md` § "Teams". Own team gets its own subsection. |
| Individual person profile | `work/companies/{slug}/people/{name}.md` for own team + adjacent. Skip distant teams. |
| Glossary, acronym lists, product nicknames | Harvest into `work/companies/{slug}/glossary.md` |
| Social / rituals / recurring events | One line each in `{slug}.md` § "Rituals" |
| **Past / closed tasks ever assigned to user** | `work/companies/{slug}/tasks/done/{YYYY-MM-slug}.md` — seeds CV record |
| Active tasks assigned now | **SKIP.** They come through weekly [[update/SKILL.md|/update]]. |
| Handbook, policies, onboarding, benefits | **SKIP.** Reference-only. |
| Confidential (HR, comp, perf reviews, customer-specific, financial) | **SKIP.** |

Track visited page IDs in-session to avoid loops.

#### 4c. Preview before writing

Show classification report:

```
Wiki scrape preview for {company}:
  - 1 company README
  - 47 project files (8 own-team — rich; 39 others — summary)
  - 23 people files (own team + adjacent)
  - 183 glossary entries
  - 62 past-task files → tasks/done/
  - Skipped: 41 handbook/policy pages, 14 confidential, 8 active tasks
```

User can drop categories, exclude specific pages, or scope down.

#### 4d. Two-pass write — same as `/start` § 6.D

**Pass D1 — write files with frontmatter + structural wiki-links.** Each file gets YAML frontmatter (`type:`, `title:`, `created:`, `updated:`, `tags:`, type-specific fields). Structural cross-refs (Owner / Team / Lead) become wiki-links at write time, even if the target file hasn't been written yet. Each project / person file gets one Log line: `- <today> — stubbed from {company} wiki during onboarding scrape`.

**Pass D2 — entity cross-link sweep.** Build slug registry from D1's files, walk each file's body, replace plain-text mentions of registered names with wiki-links (case-insensitive, word-boundary, skip code blocks and frontmatter, first occurrence per paragraph). Disambiguate ambiguous names by asking. Run `python3 system/scripts/transform.py`.

After D2, `python3 system/scripts/audit.py` should report 0 issues for the new company subgraph.

### 5. Minimum viable company file (if no wiki)

If no wiki scrape happens, at least write `memory/work/companies/{slug}/{slug}.md` from a short interview:

```
Quick stub for {company}:
1. Role / title?
2. Start date?
3. Team (if any)?
4. Stack / main tools?
5. Anything else worth recording up front?
```

The user can also answer in free text without enumerating. The agent parses prose into the same five fields and confirms the diff before writing.

Write the file with the YAML schema documented in [[memory-management/SKILL.md|Memory Management Skill]] § "Deep Memory Format" — `type: company`, `status: active (as of YYYY-MM-DD)`, `role:`, `dates:`, plus a Summary paragraph and a Log line `- <today> — onboarded.`

### 6. Atomic me.md / _current.md / old-company updates

Per [[memory/README.md|Memory README]] § "Status changes follow the dating rule", a job change is **five concurrent edits**, batched into one preview:

| File | Edit |
|------|------|
| [[memory/me.md|Me]] Current-state | `Employer: {NewCo} (as of YYYY-MM-DD)` |
| [[memory/me.md|Me]] Milestones | `- YYYY-MM-DD — started at {NewCo} → [[memory/work/companies/{slug}/{slug}.md\|{NewCo}]]` |
| [[memory/me.md|Me]] Roles table | Close prior row's date; add new row for `{NewCo}` |
| `memory/work/companies/{old-slug}/{old-slug}.md` frontmatter | `status: past (as of YYYY-MM-DD-1)` + Log line for the move |
| [[memory/work/_current.md| Current]] | Re-point at `{slug}` |

Mode-specific deviations:

- **`--side-job`** — only the side-job's own files are written. `me.md` Current-state Employer is **not** changed. A milestone line *may* be added if the user opts in: "Add 'started side job at {NewCo}' to me.md milestones?" Default is no.
- **`--client`** — same as side-job. Client engagements rarely warrant a me.md milestone unless they're a major contract; ask.
- **`--job-change`** — full five-file atomic update.
- **No flag / re-onboard** — none of the above; only the scaffold + scrape happens.

### 7. Suggested CLAUDE.md diff

Build a *proposed* CLAUDE.md update — but route it through the universal preview gate, do not auto-write:

- Add a `## Work — {NewCo}` section with the 5–10 hottest people from the scrape's own-team list, the active projects ranked by likely use, and the glossary terms that are most company-specific.
- For `--job-change` mode, propose demoting the old employer's hot-cache section to a `## Work — past employers` line that just wiki-links the company file.

Show the proposed diff. User approves, edits, or skips. If skipped, the company is fully wired into `memory/` but not promoted to the hot cache yet — fine, CLAUDE.md will catch up organically.

### 8. all-entities.md update

After step 7 (regardless of CLAUDE.md decision), build the diff for [[memory/all-entities.md|All Entities]]:

- New section header for the company under "Work — {NewCo}" if it's a major employer (job-change). Side jobs / clients sit under "Work — Prior jobs" or a new "Work — Clients" subsection.
- One line per new entity file (people, projects, glossary, how-to). Alphabetical within section.
- Cross-link the company entry: `- [[memory/work/companies/{slug}/{slug}.md|{NewCo}]] — {one-line description}`.

### 9. Scripts and report

Run in order:

```bash
python3 system/scripts/transform.py
python3 system/scripts/audit.py
```

`transform.py` regenerates `## Linked from` and normalizes frontmatter. `audit.py` should report 0 issues for the new company's subgraph; if not, fix per [[update/SKILL.md|/update]] § "Graph maintenance scripts".

Report:

```
Onboarded {NewCo}:
  - mode: {job-change | side-job | client | re-onboard}
  - company README: memory/work/companies/{slug}/{slug}.md
  - wiki scrape: {N projects, M people, K glossary terms, P past-tasks} OR skipped
  - me.md: {5 fields edited | unchanged}
  - _current.md: {flipped to {slug} | unchanged}
  - {old-slug}: {status flipped to past | unchanged}
  - all-entities.md: +X entries
  - CLAUDE.md: {applied | proposed but skipped}
  - transform + audit: 0 issues

Next steps:
  - /update once a week to sync open tasks from {NewCo}'s wiki
  - /journal each day; entries will route to {NewCo}'s tasks/people/projects
  - /update --comprehensive monthly to discover new {NewCo} teammates from chat
```

## Examples

```
User: /onboard-company newco --job-change
Agent (after pre-flight + scope question): walks NewCo wiki, classifies 312 pages
                                            scrapes own-team Payments squad richly
                                            stubs 18 own-team + adjacent people
                                            harvests ~80 glossary terms
                                            seeds 14 past tasks user had at NewCo
Preview:
  - +1 newco company README
  - +47 project files
  - +18 people files
  - +84 glossary terms
  - +14 past-task files
  - me.md: Employer flips to NewCo; old prior-co → past; +1 milestone; Roles row added
  - prior-co/prior-co.md: status → past (as of 2026-08-31)
  - _current.md: → newco
  - all-entities.md: +163 entries
  - CLAUDE.md: proposed diff (own-team people + active projects + 8 glossary terms)
Apply? [y / n / edit]

User: y
[writes everything atomically, runs transform + audit, reports clean]
```

### Example 2 — side job (no wiki connector)

```
User: /onboard-company acme-labs --side-job
Agent (after pre-flight): no wiki connector for acme-labs → skip scrape
                          falls through to § 5 minimum viable interview
Asks 5 short questions, writes:
  - memory/work/companies/acme-labs/acme-labs.md (with role: contractor, dates: 2026-05-01 – present)
  - empty people/, projects/, tasks/{active,waiting,done}/
  - all-entities.md: +1 entry under "Work — Prior jobs / Side jobs"
me.md: unchanged (user declined the milestone offer)
_current.md: unchanged
Apply? [y / n / edit]
```

### Example 3 — re-onboarding an existing employer

```
User: /onboard-company existing-co
Agent: detects memory/work/companies/existing-co/ already exists with content
       confirms: "existing-co already has files. I'll only add what's missing — no overwrites. Continue?"
       offers wiki scrape if a connector is now available
       merges scrape results: only writes files for slugs that don't exist yet
       any conflicts → previewed line-by-line, never silently merged
```

## Notes

- Re-onboarding never overwrites existing content. Conflicts go through preview.
- Slug ambiguity (e.g. user types "newco" but meant "newco-labs") → ask before scaffolding.
- If the new company shares a teammate with an old one (same person, two employers), keep two files — one per company. Cross-link them via `aliases:` in frontmatter, not by collapsing.
- Past employers stay in `memory/work/companies/` forever. Status flips, files don't move.
- For purely-personal "company-shaped" things (a band, a co-op, a research collective the user contributes to), prefer `memory/life/orgs/{slug}.md` — those aren't employers.
