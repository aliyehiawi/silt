# Journal

The daily ritual. Log what happened in 2–10 lines of free text; the agent extracts people, places, orgs, projects, and topics, and cross-files dated one-liners to the right memory entries.

> Architecture reference: [[memory/README.md|Memory README]] — that file is the source of truth for the folder shape, naming, and decision rules. This skill is the *workflow* that writes into that shape.

## Graph convention

This vault uses an **Obsidian-compatible knowledge graph** with four core rules:

1. **YAML frontmatter** on every `.md` file. Type, title, status, creation/update dates, and type-specific fields (relation, role, dates, companions, places, etc.) go in YAML at the top. The old `**Type:** ...` inline style is deprecated.

2. **Path-based wiki-links** for all cross-references: `[[path/from/root|display text]]` instead of markdown URLs. E.g.: `[[memory/life/people/friends/sarah-chen.md|Sarah Chen]]`, `[[memory/work/companies/{co}/projects/phoenix.md|Phoenix]]`. External URLs (https://) remain standard markdown links.

3. **`## Linked from` footer** auto-generated by `system/scripts/transform.py`. Lists inbound references to each file.

4. **Link entities to each other, not just through TOCs.** This is the rule that makes the graph *meaningful*. When an event happened with Anthony in Geneva, the event file should wiki-link Anthony AND the place, AND Anthony's file should wiki-link the event. Spine files (CLAUDE.md, AGENTS.md, indexes, SKILLs) are filtered out of inbound counts — only real semantic edges show up in `## Linked from`. **When parsing a journal entry, every entity mentioned should produce wiki-link edges between each other, not just appear in a TOC.**

Full spec: [[memory/README.md|Memory README]] § "Graph convention".

## Two views of your life

- **`journal/`** — immutable chronological log. Each day gets one file. Never edit past entries; they're the raw record.
- **`memory/`** — curated entity files. Each person/place/org/topic/project has one file. These get updated as things change and accumulate a dated Log of every touch.

A single `/journal` call writes to both: one daily entry, plus one appended line per touched entity.

## Directory layout (created on first run)

```
journal/
  YYYY/
    MM/
      YYYY-MM-DD.md        # one file per day
      YYYY-MM.md           # month overview + end-of-month reflection (e.g. 2026-04.md)
    YYYY.md                # year overview + year-in-review (e.g. 2026.md)
  all-time.md              # all-time TOC + major-milestones list

memory/                    # see memory/README.md for the full tree
  me.md
  glossary.md
  all-entities.md          # master TOC of every entity
  preferences.md
  work/companies/{slug}/{<slug>.md,people,projects,tasks/{active,waiting,done},glossary.md}
  life/{people,places,orgs,topics,events,health,home}/...
```

## Default workflow: `/journal <free-text>`

### 1. Ensure scaffolding

On first run (or any run where structure is missing):

- Create `journal/`, `journal/YYYY/`, `journal/YYYY/MM/` as needed.
- Create `memory/` sub-tree from `memory/README.md` if missing. Only create directories; create entity files lazily (first mention).
- If `memory/me.md` is missing, ask once: "What's your name, where do you live, and what's your current primary role? I'll seed `me.md`." Keep it short.
- If `memory/work/_current.md` is missing and the user has current employment, ask for the current company slug and seed `memory/work/companies/{slug}/{slug}.md` with role + start date.

Only ask if the info is actually needed to route today's entry. Don't front-load questions.

### 2. Append the raw entry

Open (or create) `journal/YYYY/MM/YYYY-MM-DD.md` with this format:

```markdown
---
type: journal-entry
title: YYYY-MM-DD — Weekday
created: YYYY-MM-DD
updated: YYYY-MM-DD
tags:
  - journal
  - journal-entry
---

# YYYY-MM-DD — Weekday

## Raw
{user's free-dump, verbatim — timestamp each chunk if multiple calls in one day}

## Parsed
- {domain} — [[wiki-link|entity]] — {what happened, concrete}

## Cross-filed
- ↗ [[memory/path/entity.md|Entity]]
- ↗ [[memory/path/other.md|Other]]
```

If the file already exists (multiple `/journal` calls in one day):
- Append a new timestamped chunk under `## Raw` (e.g. `### 14:32`).
- Re-run parsing on just the new chunk; append to `## Parsed` and `## Cross-filed`.

### 3. Extract entities

Parse the free-text for:

| Entity type | Signals |
|-------------|---------|
| Person | Proper nouns, "talked to", "met with", pronouns that resolve to known people |
| Place | "went to", "at the", known location names |
| Organization | "called the bank", "emailed Axa", known org names. Includes schools, universities, alliances (e.g., T4EU), banks, insurance, gov services, ISPs. |
| Institution | Schools, universities, alliances, banks, gov services (see Organization above) |
| Project | Known codenames (check CLAUDE.md + company glossaries), quoted project titles |
| **Task** | Named work items you're picking up, pushing on, or shipping — matched against slugs/titles in `work/companies/{co}/tasks/active/` and `waiting/`. "Picked up X", "shipped X", "blocked on Y for X". |
| Topic | Ongoing matters ("the visa thing", "apartment search") |
| Event | Bounded things with a date ("flew to Tunis", "Samir's wedding") |
| Glossary term | New acronyms, nicknames, or shorthand used |

**Entity routing — where to file each type:**

| Entity | Where to file | Path pattern |
|--------|---------------|--------------|
| Person (coworker) | Work folder | `work/companies/{co}/people/{slug}.md` |
| Person (family/friend) | Life folder | `life/people/{category}/{slug}.md` |
| Organization | Life orgs | `life/orgs/{slug}.md` |
| Institution (school, uni, alliance) | Life orgs | `life/orgs/{slug}.md` |
| Place | Life places | `life/places/{slug}.md` |
| Project (at company) | Work projects | `work/companies/{co}/projects/{slug}.md` |
| Topic (ongoing matter) | Life topics | `life/topics/{slug}.md` |
| Event (bounded) | Life events | `life/events/{YYYY-name}.md` |
| Task (work) | Work tasks | `work/companies/{co}/tasks/{active,waiting,done}/{slug}.md` |

For each candidate, resolve against existing files:
1. Exact slug match in the expected folder → use it.
2. Alias match (check `Also known as:` lines + `glossary.md`) → use the canonical file.
3. Fuzzy match (same first name, same org context) → propose the match, don't assume.
4. No match → stub a new file (see step 5). For tasks specifically, create the file via the rules in [[task-management/SKILL.md|Task Management Skill]].

### 4. Cross-file dated one-liners

For each resolved entity, append one line to its `## Log` section:

```
- YYYY-MM-DD — {short concrete summary, one sentence}
```

Rules:
- **Everything dated.** Every line you write to any file starts with a date. Every stub you create gets `created:` and `updated:` in YAML. Every existing file you modify has its `updated:` field bumped. No exceptions — see [[memory/README.md|Memory README]] § "Core rule: everything is dated".
- **One line per entity per day.** If the user mentions Todd three times, combine into one line.
- **Be concrete.** Not "talked to Todd" — instead "Todd — confirmed Phoenix cutover is Thursday; he'll own rollback plan → [[memory/work/companies/{co}/projects/phoenix.md|Phoenix]]".
- **Preserve what-future-me-will-want.** Names, amounts, dates, decisions, blockers.
- **Don't duplicate between the journal file and entity file.** The journal has the full context; the entity log has one distilled line.
- **Status changes get a log line, not a silent edit.** If an entity's status changes (project shipped, topic closed), append a log line *and* update the header field in YAML.
- **Retrospective entries use a coverage annotation.** If today's entry reports on a past period ("last 7 days I barely slept"), the cross-filed Log line starts `- YYYY-MM-DD — (covering YYYY-MM-DD to YYYY-MM-DD) ...`. The YYYY-MM-DD at the start is *today* (the write date). The coverage range is the period being described. This preserves the provenance of every line and keeps the rule "every line dated" intact.
- **State observations route to `life/health/log.md`.** Self-reports about sleep, mood, energy, stress, symptoms, meds — all go there, not into topic or person files. Even if the observation is caused by another entity ("hard time because of work on the side project"), the observation itself lives in the health log and *cross-references* the causing topic via a link at the end of the line.
- **Tasks get Log lines AND lifecycle moves.** When the journal mentions a task, append the line to `work/companies/{co}/tasks/{active,waiting}/{slug}.md` (not the project file alone). If the journal language implies a status change — "shipped X", "blocked on Y for X", "picked up X" — also move the task file per [[task-management/SKILL.md|Task Management Skill]] lifecycle rules and update TASKS.md. The project file gets a separate Log line only when the journal mentions the project at a level above the task (e.g., "Phoenix overall is ahead of schedule").
- **Cross-link entities to each other in the Log line.** When a line involves multiple entities, encode the relationship via wiki-links at the end of the line. If the entry says "trip to Madrid with Sarah", Sarah's Log line ends `→ [[memory/life/events/2027-03-madrid.md|Madrid]]` AND the event file's Log line ends `→ [[memory/life/people/friends/sarah-chen.md|Sarah Chen]]`. This is what builds the real semantic graph (see [[memory/README.md|Memory README]] § "Rule 4 — Link entities to each other"). Don't rely on the index files to do this work — they're TOC pointers, not semantic edges.

### 5. Stub new entities

When an entity doesn't exist yet, create the file using **YAML frontmatter** (not the old `**Type:**` style). Every stub must include:
- `type:` field (e.g., `person`, `place`, `event`, `topic`)
- `created:` and `updated:` fields (both set to today)
- `status:` field (e.g., `active (as of YYYY-MM-DD)`)
- Type-specific fields in YAML (e.g., `country:` for places, `dates:` for events, `relation:` for people)
- One Log line dated today with the triggering fact

Then list the stub in the `## Cross-filed` section so the user sees it was created.

If the entity is ambiguous (which company is "Sarah" at? is "the doctor" your GP or the cardiologist? is "Line" a friend or family?), **ask before stubbing.** One short clarifying question is cheaper than a wrong-file mess to clean up later.

### 6. Check for `me.md` triggers

Scan the parsed entry for signals that `memory/me.md` needs to change:

| Signal in entry | Trigger action |
|-----------------|----------------|
| "I moved to X" / "moving to X" | Update Current-state `Lives in:`, append dated Milestone, link to `life/home/{city-year}.md` |
| "started at X" / "new job at X" / "my first day at X" | Update Current-state `Employer:` + Milestone + flip `work/_current.md` + old company `Status: past` |
| "last day at X" / "left X" / "got laid off" | Milestone + flip the company's Status to past |
| "got married / engaged / divorced / broke up" | Update Current-state `Relationship:` + Milestone |
| "had a baby" / "kid was born" / "got a dog named X" | Update Current-state `Household:` + Milestone + possibly new entity file |
| "graduated from X" | Milestone + update Roles table if school was a prior "role" |
| "new phone number" / "new address" | Update Current-state; old value moves to a dated Log line at the bottom of me.md |
| "first time in {country}" / "first marathon" / "first X" | **Ask** before adding: "Add to life milestones?" Update only if user confirms. |

Rules:
- `me.md` changes always include a dated Milestone line — no silent edits.
- Update `updated: YYYY-MM-DD` in me.md YAML frontmatter.
- Previous values go into a dated Log line (or Roles/Places table), never deleted — full history preserved.
- **When in doubt, don't touch me.md.** A regular trip, a regular meeting, a task done is *not* a me.md event.

### 7. Update indexes

- Append a one-line summary to `journal/YYYY/MM/index.md` under today's date (create the file if missing).
- Append newly-created entity files to `memory/all-entities.md` under their alphabetical section.

Keep the daily-summary line short — one sentence, scannable:
```
- 2026-04-24 (Fri) — Phoenix migration step 3 done; prefecture dossier submitted; called mom re: summer.
```

### 8. Preview the diff, confirm, then write

Per [[memory-management/SKILL.md|Memory Management Skill]] § **Universal preview rule**, every cross-file and task move is previewed *before* writing. The only auto-write is appending the raw entry to `journal/YYYY/MM/YYYY-MM-DD.md` — that's the immutable record of what the user said. Everything derived from it (entity Log lines, task moves, stubs, CLAUDE.md promotions, `me.md` milestones, index updates) is proposed first.

Flow:

1. Build the list of proposed changes (steps 3–7 above run in "dry-run" mode).
2. Print the compact summary (see format below) ending with `Apply? [y / n / edit]`.
3. On `y` → write everything.
   On `n` → discard; nothing beyond the raw entry is written.
   On `edit` → let the user inline-adjust the diff (e.g. fix a misparsed entity, drop a wrong cross-file), then re-ask.

Summary format:

```
Journaled 2026-04-24:
  entry:       journal/2026/04/2026-04-24.md
  touched:     4 existing, 1 new
  cross-filed:
    ↗ memory/work/companies/{co}/tasks/active/phoenix-cutover-runbook.md  (+1 line)
    ↗ memory/work/companies/{co}/projects/phoenix.md                      (+1 line)
    ↗ memory/life/places/prefecture-paris-13.md                               (+1 line)
    ↗ memory/life/topics/carte-de-sejour-renewal.md                           (+1 line)
    ↗ memory/life/people/family/mom.md                                        (new stub, +1 line)
  tasks:       0 moved
  CLAUDE.md:   no changes
```

If a task was moved (e.g. shipped → done), the diff includes it explicitly:
```
  tasks:       1 moved
    ↗ active/phoenix-step-3.md → done/2026-04-phoenix-step-3.md  (shipped)
```

The diff always ends with `Apply? [y / n / edit]`. Nothing below the raw-entry write happens until the user answers.

If the user said `y` and then later says "undo that" or "that's wrong", revert by removing the appended lines (they're dated and atomic).

### 8.5 Transform the graph

After the user approves and writes the diff, run:
```
python3 system/scripts/transform.py
```

This idempotent script refreshes wiki-links, regenerates `## Linked from` sections across the vault, and ensures all files conform to the Obsidian graph convention. Safe to run multiple times.

### 9. Commit and print push hint (default `/journal` only)

After step 8 (write) and step 8.5 (graph transform) both complete following a `y` confirmation, stage and commit the changes. **Push is never automatic** — print the push command and stop.

**Scope.** This step fires *only* on the default workflow `/journal <free-text>`. It does **not** fire on sub-commands (`--search`, `--on`, `--reflect`, `--reindex`, `--prune`), on `/start`, on `/update`, or on any manual edit performed outside the journal flow. The wider rule lives in [[CLAUDE.md|CLAUDE.md]] § Git policy.

Run, in order:

```bash
git add journal/ memory/ CLAUDE.md TASKS.md
git diff --cached --quiet && exit 0   # nothing staged → silent no-op
git commit -m "journal: YYYY-MM-DD"
```

`YYYY-MM-DD` is the *journal entry's date* (the file written in step 2), not today's calendar date — they differ when back-filling.

On success, print exactly this, with the short SHA filled in:

```
✓ Committed journal entry for YYYY-MM-DD (<short-sha>).
To push to main: git push
```

Then stop. Do **not** run `git push`. Do **not** propose a PAT, an HTTPS remote, or any auth setup — pushing belongs to the user's terminal, where their SSH key works.

If the commit fails (most commonly: nothing staged because the preview was a no-op), surface a single-line note and move on. No retry loop.

## Sub-commands

### `/journal --search <query>`

Fast retrieval. Strategy:
1. Resolve the query to an entity (person/place/topic) via `memory/all-entities.md` + `glossary.md`.
2. If it's an entity → open its file, show the Log section, offer to pull the full journal entries that mention it.
3. If it's a date or date range (e.g. "last week", "March 2026") → list matching journal files with one-line summaries.
4. If it's free-text → grep `journal/` and `memory/`, rank by recency + hit density.

### `/journal --on <date>`

Show the journal entry for a specific date, or the nearest one if that day is blank.

### `/journal --reflect`

Weekly or monthly reflection pass. Read the last 7 (or 30) daily entries and ask the user:
- What went well this week/month?
- What's nagging at you?
- Any new topic that deserves its own file?
- Any stale topic that can be archived?

Append the reflection to the appropriate `index.md` (monthly index for weekly reflections, year index for monthly reflections). This is how the system grows a *narrative* on top of the raw log.

### `/journal --reindex`

Rebuild `memory/all-entities.md` from the file tree. Useful after manual edits or file moves. Purely mechanical — no content changes.

### `/journal --prune`

Quarterly hygiene. Scan for:
- Entity files not touched in 12+ months → propose archive (`Status: archived`, move to `archive/` subdirectory).
- CLAUDE.md entries whose underlying entity hasn't been touched in 60 days → propose demotion out of the hot cache.
- Topic files marked "in progress" but with no recent log → ask if they're done.

Always propose, never auto-archive.

## Connector enrichment (optional)

If MCP connectors are available (chat, calendar, wiki, etc.), the journal can enrich entries — but **nothing external is stored on disk**. Connectors are transient input surfaces only. See [[memory/README.md|Memory README]] → "External sources — ephemeral inputs".

- After a daily entry, offer: "Want me to scan today's calendar / chat mentions for things you didn't mention?"
- Found items become **proposed additions** — user confirms, then they're written as regular journal/entity content in plain prose. No URLs, no message IDs, no "last synced" fields on anything that lands on disk.
- On `--reflect`, scans can surface candidate topics for the reflection — still user-approved, still plain prose.
- People-discovery from chat is the responsibility of `/productivity:update --comprehensive`, not the daily journal.

Never auto-scrape without asking. Privacy first.

## Interaction conventions

- **Natural input, no syntax.** The user types what happened. You do the parsing.
- **Ambiguity → one question.** Don't batch 5 clarifying questions. Ask the most important one, proceed with best guess on the rest, flag them in the diff for review.
- **Preview before write.** The diff is always shown with `Apply? [y / n / edit]` before any derived files are touched. See [[memory-management/SKILL.md|Memory Management Skill]] § Universal preview rule.
- **Short confirmations.** After the user approves, the diff is the receipt. Don't narrate.
- **Respect work/life separation.** When parsing, tag each extracted item as work or life. Never cross-file a personal item under a company folder or vice versa.
- **Never rewrite past journal entries.** They're the historical record. If a fact turns out to be wrong, note the correction in today's entry; don't edit yesterday's.

## Examples

### Minimal daily entry

User: `/journal worked on phoenix step 3 with sarah, went to prefecture and submitted the carte de séjour, called mom about summer trip to tunisia`

Agent:
1. Parses: Phoenix (project), Sarah (work person), prefecture (life place), carte de séjour (life topic), mom (life person, family), summer trip (life event — bounded, upcoming).
2. Appends to `journal/2026/04/2026-04-24.md`.
3. Cross-files one-liners to: `phoenix.md`, `sarah-chen.md`, `prefecture-paris-13.md`, `carte-de-sejour-renewal.md`, `mom.md`. Stubs `2026-tunisia-summer.md` for the event (asks first).
4. Updates `journal/2026/04/index.md`.
5. Shows diff.

### Retrieval

User: "when did I last go to the prefecture?"

Agent: reads [[memory/life/places/prefecture-paris-13.md|Prefecture (Paris 13)]], returns the most recent Log line with its date and context.

User: "what was I up to with Sarah last month?"

Agent: reads [[memory/work/companies/{co}/people/sarah-chen.md|Sarah Chen]], filters Log lines from last month, offers to open the underlying journal entries for full detail.

User: "what cities did I visit in March 2025?"

Strategy (two paths, cross-check each other):

1. **Via events.** List `memory/life/events/2025-03-*.md`. Each event file has a `places:` header and `dates:` in its YAML frontmatter. Union the cities across all March 2025 events.

2. **Via places.** `grep -l "^- 2025-03" memory/life/places/*.md` returns every place file with a log entry in March 2025. Filter by `type: place` with a `country:` field in YAML.

Return result as a table with date, city, country, linked event:

```
| Date        | City     | Country | Event                              |
|-------------|----------|---------|------------------------------------|
| 2025-03-04  | Lisbon   | Portugal| [[memory/life/events/2025-03-lisbon-weekend.md|2025-03-lisbon-weekend]] |
| 2025-03-18  | Tokyo    | Japan   | [[memory/life/events/2025-03-japan-with-line.md|2025-03-japan-with-line]] |
| 2025-03-20  | Kyoto    | Japan   | [[memory/life/events/2025-03-japan-with-line.md|2025-03-japan-with-line]] |
| 2025-03-22  | Osaka    | Japan   | [[memory/life/events/2025-03-japan-with-line.md|2025-03-japan-with-line]] |
```

If the two paths disagree (a city in a place file but not in any event, or vice versa), surface the discrepancy so the user can reconcile.

User: "who did I travel with in 2024?"

Strategy: list all `memory/life/events/2024-*.md` files, collect `companions:` from each, deduplicate. One grep + a union.

User: "what was going on with the carte de séjour 6 months ago?"

Strategy: read [[memory/life/topics/carte-de-sejour-renewal.md|Carte de Séjour Renewal]] Log section, filter to the relevant date window. If the file has since been archived, check `memory/life/topics/archive/`.

User: "analyse my personality last month" / "summarize my 2026"

Strategy: this system doesn't pre-compute inferences about you. Collect the raw source material and hand it to the LLM in the request:
1. Gather all `journal/YYYY/MM/YYYY-MM-DD.md` files in the requested window.
2. Concatenate them (they're small — a month is ~30 KB).
3. Pass to the LLM with a prompt like "summarize themes, tone shifts, and recurring patterns in these journal entries." No pre-written personality file involved — the journal itself is the source of truth.

### Trip scenario (multi-entity write)

User: `/journal went to japan for 10 days with line, did tokyo, kyoto, osaka, ate a lot of ramen, visited fushimi inari shrine in kyoto`

Agent (entry date 2026-04-24, trip implicitly last 10 days):

1. **Ambiguity check (one question batch):** "Is Line a friend, family, or partner? Pin the trip to specific dates (e.g. 2026-04-14 to 2026-04-23) or keep it approximate? And — since no prior Japan place files exist — is this your **first time in Japan**? If yes, I'll add a milestone to me.md."

2. **Writes today's journal** at `journal/2026/04/2026-04-24.md`:
   - `## Raw` — verbatim user text
   - `## Parsed` — event: Japan trip (10 days); people: Line; places: Tokyo, Kyoto, Osaka; place: Fushimi Inari shrine (Kyoto); highlight: ramen
   - `## Cross-filed` — list of 5 files written

3. **Creates event file** `memory/life/events/2026-04-japan-with-line.md`:
   ```markdown
   ---
   type: event
   title: Japan trip with Line (April 2026)
   status: completed (as of 2026-04-24)
   created: 2026-04-24
   updated: 2026-04-24
   dates: 2026-04-14 to 2026-04-23
   companions: "[[memory/life/people/friends/line.md|Line]]"
   places: "[[memory/life/places/tokyo.md|Tokyo]], [[memory/life/places/kyoto.md|Kyoto]], [[memory/life/places/osaka.md|Osaka]]"
   tags:
     - life
     - event
   ---

   # Japan trip with Line (April 2026)

   ## Summary (as of 2026-04-24)
   10-day trip to Japan with [[memory/life/people/friends/line.md|Line]]. Visited [[memory/life/places/tokyo.md|Tokyo]], [[memory/life/places/kyoto.md|Kyoto]], and [[memory/life/places/osaka.md|Osaka]]. Highlights: lots of ramen, [[memory/life/places/fushimi-inari-shrine.md|Fushimi Inari shrine]].

   ## Key facts
   - (as of 2026-04-24) 10 days total
   - (as of 2026-04-24) Cities: Tokyo, Kyoto, Osaka

   ## Log
   - 2026-04-24 — trip recorded after return
   ```

4. **Creates / updates person file** `memory/life/people/friends/line.md` (if new stub):
   ```markdown
   ---
   type: person
   title: Line
   relation: friend
   status: active (as of 2026-04-24)
   created: 2026-04-24
   updated: 2026-04-24
   tags:
     - life
     - person
   ---

   # Line

   ## Summary (as of 2026-04-24)
   [to be filled — ask user on next mention]

   ## Log
   - 2026-04-24 — 10-day Japan trip together (Tokyo, Kyoto, Osaka) → [[memory/life/events/2026-04-japan-with-line.md|Japan trip with Line]]
   ```

5. **Creates / updates each city file**, e.g. `memory/life/places/tokyo.md`:

   title: Tokyo
   country: Japan
   status: visited (as of 2026-04-24)
   created: 2026-04-24
   updated: 2026-04-24
   tags:
     - life
     - place
   ---

   # Tokyo

   ## Summary (as of 2026-04-24)
   City in Japan. First visited April 2026.

   ## Log
   - 2026-04-24 — visited during Japan trip with [[memory/life/people/friends/line.md|Line]] → [[memory/life/events/2026-04-japan-with-line.md|Japan trip with Line]]

### Multi-day retrospective + state observation

**Setup (over a week of daily entries):**

Day 1 (2026-04-18) — user: `/journal started working on a personal project — voice note transcriber app`

**Day 7 (2026-04-24) — user:** `/journal last 7 days i have only slept 4 hours because of work on the app and i am having hard time but managing`

## Notes for scale (10–20 years)

- Daily files stay small (~1 KB each). 7,300 files after 20 years is trivial.
- Entity log lines are tiny and greppable. `grep -h "^- " memory/life/places/prefecture-paris-13.md` gives you every visit over 20 years in one view.
- When a single entity's Log exceeds ~500 lines, split per [[memory/README.md|Memory README]] archival rule.
- When a company folder or topic is closed out, archive (don't delete). Future-you will want the record.
- The monthly and yearly indexes are what keep navigation human-scale — they're worth the 2-minute investment at month/year boundaries.
